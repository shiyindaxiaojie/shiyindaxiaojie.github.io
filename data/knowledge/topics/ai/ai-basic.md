# 前言

很多人第一次接触 AI，最容易卡在一堆新词里。

LLM、Prompt、RAG、Agent、MCP、Context Engineering、Loop Engineering，听起来像是大公司在造新词，其实是有关联的。
1. LLM 是大语言模型，负责理解和生成。
2. RAG 负责把外部资料翻出来，塞进模型这次要看的上下文里。
3. Agent 负责拆任务、调工具、看结果、继续做。
4. Engineering 工程方法负责让这一整套东西在真实项目里跑稳，而不是靠一次灵感爆发。


# LLM 大语言模型

LLM 全称为 Large Language Model，即大语言模型。

你平时用的 ChatGPT、Claude、Gemini、DeepSeek、豆包，底层都离不开大语言模型。

它最核心的能力不是像人一样思考，而是根据上下文预测下一段最可能出现的内容。这个说法听起来有点冷，但能力已经足够吓人，它能写文章、总结资料、改代码、翻译、做分析，也能陪你把一个模糊想法一点点聊清楚。

但 LLM 单独用，有几个硬伤。

- 它只靠当前上下文和训练中学过的知识回答，容易答旧信息。
- 它看不到你的私有资料，除非你把资料给它。
- 它不能真的替你操作系统，除非接了工具。
- 它没有天然的长期记忆，换个会话很多信息就断了。
- 它容易把听起来合理的内容编出来，所以事实问题必须验证。

所以，LLM 更像一个很强的语言大脑。

能聊，能推理，能生成。

但要让它真正干活，还得给它资料、工具、记忆和流程。

# Prompt 是最小的控制杆

Prompt 就是你给模型的任务说明。

它不神秘。好的 Prompt 通常把几件事讲清楚。

- 你要它完成什么任务。
- 背景材料是什么。
- 输出给谁看。
- 输出格式长什么样。
- 哪些边界不能碰。

一个很普通但好用的写法是这样。

```text
你是一个后端架构师。
请阅读下面的故障日志，判断最可能的原因，按排查顺序输出。
只基于日志和我给出的背景判断，不要编造环境信息。
输出分为现象、判断、下一步验证。
```

Prompt 能解决表达问题，不能解决资料问题。

如果模型没看过你的代码规范、业务文档、线上日志，你把 Prompt 写得再漂亮，它也只能猜。

这时就轮到 RAG 和 Context Engineering 上场了。

# RAG 是让模型开卷

RAG 是 Retrieval-Augmented Generation，检索增强生成。

你可以把它理解成，回答前先翻资料。

它的流程很朴素。

- 离线阶段，把 PDF、Markdown、网页、数据库记录切成小块。
- 再把这些文本块转成向量，存进向量数据库。
- 用户提问时，把问题也转成向量。
- 系统找出最相关的文本块。
- 模型带着这些文本块回答。

所以 RAG 的价值不是让模型变聪明，而是让模型回答时有证据。

公司内部知识库、客服问答、产品文档、代码库问答，都很适合 RAG。

但 RAG 不是万能药。文档切得太碎，答案会断。检索召回错了，模型会拿错材料回答。资料本身过期，回答也会跟着错。

RAG 真正难的地方，不是接一个向量库，而是让正确材料在正确时机出现。

## GraphRAG

传统 RAG 擅长找相似片段，但它不擅长回答关系型问题。

比如你问，一家公司过去三年战略变化和组织调整有什么关系。答案可能散在年报、访谈、新闻、会议纪要里，单靠相似度找几个片段，很容易只看到局部。

GraphRAG 会先从文档里抽取实体和关系，构建知识图谱，再基于图谱做检索和总结。

它适合这种场景。

- 文档很多，彼此之间关系复杂。
- 问题偏宏观，需要跨文档整合。
- 你关心实体之间的关系，而不是只找某个段落。

代价也很现实。构图、聚类、摘要都要成本，更新也比较重。资料经常变的小系统，直接上 GraphRAG 可能有点过。

## LightRAG

LightRAG 可以看成更轻的图增强 RAG。

它也抽实体和关系，但省掉了 GraphRAG 里很重的社区检测和社区摘要，把实体、关系和文本一起做检索。

它的思路更工程化。

- 低层关键词找具体实体。
- 高层关键词找抽象关系。
- 新文档来了，尽量增量更新，不重建全量图谱。

如果你需要一点图谱能力，又不想把成本拉太高，可以先看 LightRAG 这一类方案。

# Agent 是会循环干活的系统

Agent 不是一个更会聊天的模型。

Agent 是 LLM 在循环中自主使用工具的系统。

一个最小 Agent 通常有这几块。

- 大脑，负责理解任务和判断下一步。
- 规划，负责把大目标拆成小步骤。
- 记忆，负责保存当前任务状态和长期经验。
- 工具，负责搜索、读文件、写代码、查数据库、调用 API。
- 循环，负责观察结果，再决定下一步。

拿写代码举例。

普通 LLM 会告诉你怎么改。

Coding Agent 会读取仓库、定位文件、修改代码、运行测试、根据报错继续修。

这就是区别。

## Agent 和 Workflow

Workflow 是开发者提前写好的流程。

每一步做什么，下一步去哪，基本由代码决定。它稳定、便宜、容易排查，适合步骤清楚的业务。

Agent 是模型自己决定下一步。

它更灵活，能处理开放问题，也更贵、更不稳定、更难排查。

所以真实项目里别急着全 Agent 化。流程固定就用 Workflow，流程开放再引入 Agent。很多生产系统，其实是 Workflow 控大链路，Agent 处理里面最不确定的那几段。

## Agent 常见工作模式

ReAct 是边想边做。

模型先思考，再调用工具，再看结果，然后继续下一轮。它透明、通用，但容易耗 token，也可能卡在循环里。

Plan-and-Execute 是先计划再执行。

模型先把步骤列出来，再按计划做。它更省，但遇到变化时需要重新规划。

Reflection 是做完再检查。

一个 Agent 自查，或者两个 Agent 一个写一个审。写代码、合同、方案这类任务，很适合加这一层。

Multi-Agent 是多人协作。

规划、研究、开发、测试拆给不同 Agent。它适合复杂任务，但别太早用。很多时候，一个强模型加好工具，比一堆弱 Agent 互相传话更靠谱。

# Function Call、MCP、Skills 分别管什么

Function Call 解决的是模型怎么调用函数。

模型不直接执行函数，而是输出一个结构化调用请求，外部程序执行后把结果交回模型。

MCP 解决的是工具怎么标准化接入。

以前每个产品都要单独接文件、数据库、浏览器、GitHub、Slack。MCP 把这些能力包装成统一协议，让支持 MCP 的客户端可以接不同服务器。

Skills 解决的是怎么把做事方法沉淀下来。

比如一个团队有固定的代码审查流程、文章写作规则、发布检查清单，就可以写成 Skill。Agent 每次做类似任务时先读规则，不用靠人一遍遍提醒。

你可以这样记。

Function Call 是能力层。

MCP 是连接层。

Skills 是方法层。

# AI 工程方法怎么区分

这几年 AI 圈的新词很多，但主线不复杂。

Prompt Engineering 解决怎么把话说清楚。

典型问题是，任务怎么描述，角色怎么设定，输出格式怎么约束。

Context Engineering 解决该给模型看什么。

它关心的不是一句 Prompt，而是这次调用里所有信息，包括用户输入、历史对话、检索资料、工具结果、任务状态、系统规则、安全边界。

Harness Engineering 解决怎么让 Agent 在真实环境里稳定做对。

它不是让模型更聪明，而是把运行环境搭好。比如 AGENTS.md、目录约束、测试、lint、权限、日志、Git Hook、CI、代码审查、回滚机制。

Loop Engineering 解决怎么让任务循环自己转起来。

以前是你写一条 Prompt，等结果，再写下一条。Loop 的目标是把触发、派发、执行、验证、记录状态、人工审批这些环节串成循环。

这时你的工作就从写 Prompt，变成设计一个能反复产出结果的系统。

听起来很爽，但别跳步。

一次手动任务都没跑稳，就急着做自动循环，后面很难判断问题出在模型、上下文、工具、状态，还是验证闸门。

# 可以直接用什么

别一上来纠结哪个最强，先按场景选入口。

日常问答、写作、总结资料，可以用 ChatGPT、Claude、Gemini、DeepSeek、Kimi、Qwen、豆包。

搜索和研究，可以用 Perplexity、ChatGPT Deep Research、Gemini Deep Research、Kimi 研究类能力。

写代码和改项目，可以用 Codex、Claude Code、Cursor、GitHub Copilot、Windsurf、Trae。

做知识库和 RAG，可以看 Dify、Coze、FastGPT、LlamaIndex、LangChain。

做 Agent 应用，可以看 OpenAI Agents SDK、LangGraph、CrewAI、AutoGen。

做自动化，可以把 n8n、Make、Zapier 和模型能力接起来，让它们处理通知、表格、工单、邮件、数据同步。

选择时别只看演示视频，直接问 4 个问题。

- 它能不能接你的真实资料。
- 它能不能调用你需要的系统。
- 它有没有权限和审批控制。
- 它出错后，你能不能定位和回滚。

答不上来，就别急着放进生产链路。

# 普通人怎么开始用

最实用的路径不是背概念，而是从一个真实任务开始。

找一个你每天都在重复的小任务。

比如整理会议纪要、总结文章、写周报、查日志、改一个小脚本、把 Excel 数据变成图表。

然后按这个顺序练。

1. 让模型复述任务，确认它理解对了。
2. 把材料给足，别让它猜。
3. 要求它输出可执行结果，而不是泛泛建议。
4. 让它自查一次，特别是事实、边界、遗漏。
5. 把好用的 Prompt、资料、检查清单沉淀下来。

一开始可能不会省时间，甚至会更慢。

这很正常。

真正的变化通常发生在你把第 5 步做起来之后。你不是每次重新问一遍，而是在给自己搭一套越来越顺手的工作环境。

# 常见误区

AI 不是搜索引擎替代品。

事实问题要看来源，重要结论要验证。模型回答得很顺，不等于它答对了。

Prompt 不是越长越好。

上下文要准，不是多。把无关材料塞满，只会让模型更难抓重点。

RAG 不能消灭幻觉。

它只是让模型更容易基于资料回答。检索错、资料错、切分错，照样会错。

Agent 不等于自动靠谱。

它能自己决定下一步，也会自己走偏。越能行动，越需要权限、测试、审批和回滚。

多 Agent 不一定更强。

如果任务本身不需要分工，多 Agent 只是在增加沟通成本。

# 如果只记一件事

AI 的基础地图可以压成 4 层。

LLM 让机器会理解和生成。

RAG 让它回答前能翻资料。

Agent 让它能调用工具并循环干活。

工程方法让它在真实项目里少犯错、可验证、能复用。

先把这 4 层分清，再去学具体产品和框架，会轻松很多。
